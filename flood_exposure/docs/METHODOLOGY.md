# 方法与业务口径说明

## 1. NoData 的业务含义

水深栅格中两类“看起来都是零/空”的值必须严格区分：

| 类别 | 数值含义 | 业务解释 | 处理方式 |
| --- | --- | --- | --- |
| **有效零值 (valid zero)** | 像元被模型覆盖，水深确认为 0 m | “确认未淹” | 计入干地面积 `dry_area`，参与面积权重 |
| **NoData** | 像元无可用水深（模型域外、被掩膜、传感器缺测等） | **“不知道”**，既不是干地也不是淹地 | 计入 `nodata_area`，披露缺测比例；**禁止按零填补** |
| **栅格外 (OOB)** | 人口格的一部分落在水深栅格覆盖范围之外 | 同样是“不知道” | 计入 `oob_area`，与 NoData 合并为缺测 |

判定优先级：掩码数组的 mask → 浮点 NaN → 与栅格原生 dtype 的 nodata
标量比较。比较保持在栅格原生 dtype（例如 float32 的 `-9999` 不提升为
float64），避免大整数填充值的精度错配。

**发布闸门**：每个 (流域, 时次) 的

```
missing_fraction = (nodata_area + oob_area) / area(B ∩ 人口网格)
```

分母是**该流域被人口网格覆盖的面积**（各人口格 `area(B∩P)` 之和），
不是整个人口格面积。超过配置的 `max_missing_fraction` 时，该运行拒绝发布
（`PublishGateError`），暂存区整体销毁，`releases/current` 保持指向上一完整
版本。系统不会用 0 替代 NoData 来“凑出”一个结果。

人口网格自身的 NoData 格不赋零人口，而是整体剔除并打 `POP_RASTER_NODATA`。

## 2. 面积权重定义

所有几何运算在**等面积投影**（默认 EPSG:6933，WGS 84 / NSIDC EASE-Grid 2.0
等面积圆柱）下进行。选它而非以中央经线为界的 LAEA/AEA，是为了统一处理
跨越 ±180° 经度环绕线的流域（见第 5 节）。

对人口网格像元 P（四角从其原生 CRS 投影到工作 CRS 后的四边形）与流域 B：

```
w(B, P) = area( intersection(B, P) ) / area(P)        # ∈ [0, 1]
```

水深源像元 s 到人口格 P 的面积贡献按源像元类别累加。**关键约束**：归到
流域 B 的各类面积必须是三向交集，即水深像元、人口格、流域三者的公共部分，
而不能用“流域占格比例 × 格内类别比例”的乘积代替 —— 后者丢掉了类别在格内
的位置，会把格一侧的洪水或 NoData 错误地算到另一侧流域：

```
A_wet(B, P)    = Σ_s area(s ∩ P ∩ B)  ，depth(s) > 阈值 且 s 有效
A_dry(B, P)    = Σ_s area(s ∩ P ∩ B)  ，depth(s) ≤ 阈值 且 s 有效（含有效零）
A_nodata(B, P) = Σ_s area(s ∩ P ∩ B)  ，s 为 NoData
A_oob(B, P)    = area(B ∩ P) − 以上三者
```

### 2.1 受淹人口

人口在原人口格内按面积均匀分布，因此受淹人数按真实受淹交集占**原格**的
面积份额计算；流域在格内“拥有”的人口则按 `area(B∩P)/area(P)` 计算：

```
exposed_pop(B, t) = Σ_P pop(P) · A_wet(B,P,t) / area(P)
weighted_pop(B)   = Σ_P pop(P) · area(B∩P)     / area(P)
```

NoData/OOB 不进入 `A_wet`，因此该估计是**保守下界**；缺测规模通过
`missing_fraction` 与质量标记单独披露，而不是被悄悄当作干地。

### 2.2 相邻流域重叠

当流域 B1、B2 的边界轻微重叠时，重叠区内的人口格 P 与两个流域分别求交，
各自只拿到份额 `w(B1,P)`、`w(B2,P)`：

- 任何一方都不会仅凭“格与我相交”就拿到整格人口（权重 1）；
- 两个份额可能之和 > 1（重叠是数据质量问题，不应靠裁剪隐藏）；
- 重叠对与重叠面积写入计算清单，相关行打 `OVERLAP_WEIGHTED`。

不变量：**同一条人口记录不可能被两个流域同时全额计数**（测试
`test_overlapping_basins_share_cells_by_area_not_double_counted`）。

## 3. 窗口读取与结果确定性

- 源水深栅格按 `window_tile_size` 分块从磁盘读取（`rasterio.windows.Window`），
  窗口只决定每次 I/O 的像元范围；
- 每个像元的 `area(s ∩ P ∩ B)` 由几何唯一确定，与它在哪个窗口被读到无关，
  因此改变 tile 尺寸权重与类别面积均不变（测试要求差值 < 1e-6）；
- 累加器只做加法，满足交换律/结合律，分块顺序（正序、逆序、乱序）结果
  在声明精度 `DECLARED_PRECISION = 1e-6` 内一致；
- 回归样例 `test_spatial_attribution.py` 用独立的小网格几何求交核对受淹/
  干地/缺测/OOB 面积与受淹人数，并在不同工作 CRS、不同 tile 下复算。

## 4. 边界增量处理

权重表只依赖（流域几何指纹, 人口网格 sha256, 人口网格变换/CRS, 工作 CRS,
代码版本），**与水深栅格无关**。缓存键是上述要素的稳定 JSON 哈希：

- 几何指纹未变的流域 → 命中缓存，跳过全部几何相交；
- 几何修订/新增流域 → 指纹变化，重建权重表；
- 修复失败流域 → 不产出、不进缓存，计入 `failed_basins`；
- 换一批预报时次 → 全部权重表天然复用。

演示：v1→v2 中 B 局部修订、D 退化为修复失败、E 新增，运行结果为
缓存命中 `[A, C]`、重建 `[B, E]`、失败 `[D]`。

## 5. 无效几何与经度环绕线

- `shapely.make_valid`（GEOS MakeValid）修复自相交等问题，成功打
  `INVALID_GEOM_REPAIRED`；若修复后没有任何有面积的多边形（如纯线串
  退化几何），返回 `GEOM_REPAIR_FAILED`，该流域被跳过且受
  `max_invalid_basin_fraction` 闸门约束；
- 跨 ±180° 的几何按经度跨度 >180° 识别，平移到 [0,360] 空间在 180° 处
  切开，再把东半部分平移回 [-180,180]，得到 MultiPolygon 进入后续流程。

## 6. 暂存再发布与中断安全

```
staging/<run_id>/  —写中间结果→  releases/<run_id>/  —rename(2)→  current
```

- 所有写操作先落 `*.tmp` 再 `os.replace`；
- 发布是目录整体 `rename` + 符号链接原子切换，读者任何时刻只能看到
  完整版本；
- SIGTERM/SIGINT 置中止标志，运行器在检查点抛 `KeyboardInterrupt`，
  上下文管理器销毁暂存区，`current` 不动；
- 下次启动清理 `staging/` 全部残留。

## 7. 独立参考计算

`reference.py` 用与主流水线**完全独立的代码路径**（规则点阵 / lattice
Monte Carlo）复核：在每个人口格铺 K×K 个点阵点，逐点判定落在水深像元的
哪个类别，以点数比例估计面积比例。两条路径只共享输入文件与坐标变换，
几何求交与面积累加不共用。K=48 时限 0.06（O(1/K) 边界误差），演示中
实测最大偏差约 7e-4。

## 8. 质量标记枚举

| 标记 | 触发条件 |
| --- | --- |
| `OK` | 无任何异常 |
| `NODATA_PRESENT` | 水深 NoData 面积 > 0（未超闸门） |
| `NODATA_GATE_FAIL` | 缺测比例超上限，发布被拒 |
| `OUT_OF_DEPTH_EXTENT` | 显著面积落在水深栅格外 |
| `OVERLAP_WEIGHTED` | 与相邻流域存在重叠，已按面积分摊 |
| `INVALID_GEOM_REPAIRED` | 边界无效但修复成功 |
| `GEOM_REPAIR_FAILED` | 修复失败，流域未参与计算 |
| `POP_RASTER_NODATA` | 人口网格自身含 NoData 格 |

## 远程水深的可恢复传输（不改统计口径）

供应商把水深 GeoTIFF 放在 HTTP 上，连接经常中断。`flood-exposure fetch`
只负责**把字节完整、可核对地搬到本地**，随后仍由原有 `make-inventory`
按 sha256 生成清单、由 `run` 计算暴露度；下载器不参与任何面积/权重/NoData
判定，因此统计口径与本地文件输入完全相同。

完整性判定按以下顺序，任何一步不满足都不会替换目标：

1. 首次探测的**强 ETag、总长度、请求 URL、最终 URL** 与本地进度一致；
2. 每个已确认块的区间被读取的真实字节覆盖，且区间内容 SHA256 与记录一致；
3. 全部区间 [0, total-1] 被不重叠块覆盖；
4. 临时文件**实际长度**等于对象总长度；
5. 逐块再按磁盘真实内容复核；
6. 若给定期望摘要，整个对象的 SHA256 相符。

`Content-Range` 的起止与总长度、`Content-Length` 与区间长度、真实读到的
字节数逐项核对；中途断连或短体不会留下“已确认块”。服务器忽略 Range
返回 200 时，作废本轮分段进度并从 0 流式重传，重传前再次核对身份与长度。
416 只有在本地全部区间已校验且长度一致时才进入最终核对，否则视为协议错误。

并发方面，同一目标由 `flock` 独占：后来的进程立即以退出码 3 报占用；
进程异常退出时内核自动释放锁，新进程可直接接管已校验的块。

# 从 DEM 推导汇水边界：`delineate`

`delineate` 用**高程栅格自身**推导排水拓扑，因此不需要预先画好的流域
边界。它回答“水往哪里流、哪些格子会流到哪个测站”，输出的是**地形推导的
汇水边界**——不是洪水水动力模拟，也不含水深、流速或淹没范围。

## 9. 输入

### 9.1 DEM

- 单波段 GeoTIFF，驱动必须是 GTiff（含 COG）；
- CRS 必须是**米制投影**：地理坐标（度）与非米单位（英尺等）明确拒绝；
- 仿射变换必须**北向上**、无旋转/错切（`b = d = 0`, `a > 0`, `e < 0`），
  像元 `dx`、`dy` 可以不同。

### 9.2 有效格

```
valid = 数值有限 (非 NaN/Inf) 且 未被 NoData 掩膜/掩码
```

无效格保留原始数值供追溯，但**永不参与排水**：它是不可穿越的屏障，也
不是泄水口。掩码数组、`nodata` 元数据值、NaN 三种来源分别记录在
`invalid_reason`（1 = 非有限，2 = NoData）。

### 9.3 测站 CSV

必需列 `outlet_id, row, col`（列名大小写不敏感，忽略首尾空白）。`row/col`
从 0 开始、指向原图**像元中心**，**不做自动吸附**。显式拒绝：

| 情况 | 错误信息要点 |
| --- | --- |
| 行列非整数 | “不是整数；行列必须是从 0 开始的整数格坐标” |
| 落在图外 | “row=… 在图外；有效行范围 0..H-1” |
| 落在无效高程 | “落在无效高程格 … 被 NoData 掩膜 / 高程为 NaN” |
| 两个不同 ID 占同一格 | “两个不同测站占同一格 (row=r, col=c): 'A' 与 'B'” |
| 同一 ID 指向不同格 | “同一 outlet_id 'A' 指向不同格: (r0,c0) 与 (r1,c1)” |
| 缺列 | “缺少必需列 ['col']；现有列: [...]” |

## 10. 算法（每次运行的固定决策都写入 `summary.json`）

### 10.1 填洼：只抬高、只从外圈有效格出发

优先漫水（priority-flood）：把图像**最外圈的有效格**作为唯一泄水口入堆，
按高程非降序弹出，遇到未访问的有效邻格时把它的高程抬到当前水位。结果是

- 每个有效格都能沿一条**不升高**的路径走到最外圈有效格；
- 已能排水的坡面保持原高程（弹出的水位不会高于它自身，除非它是洼地）；
- 内部洼地被填平，`raised = filled - original >= 0`；
- 无效格是屏障，永不入堆，因此填洼路径不会穿过 NoData。

若某个有效 8 邻域连通块**完全不接触外圈**（例如被 NoData 环包围），
不猜出口、不穿 NoData，直接抛 `NoOutletError`，报告该块的行列范围、
格数与面积，退出码 3。

### 10.2 D8 单流向

对每个有效格：

1. 若存在**更低**的有效邻格，坡度 `s = (z_c - z_n) / dist(c,n)`：
   - 正交距离为 `dx` 或 `dy`，对角为 `hypot(dx, dy)`；
   - **长宽不同**时同一高差在对角/正交上的坡度不同，最陡方向会随之改变；
   - 取坡度最大的邻格；**等坡度按固定顺序 NW,N,NE,E,SE,S,SW,W（编码 0..7）
     取第一个**，与遍历顺序、CSV 行序无关。
2. 若没有更低图内邻格：
   - 该格在最外圈 → 写 `8`（OUTSIDE，流出图）；
   - 否则它属于同高程平台，进入平地展开。

### 10.3 平地展开（不靠微斜坡）

填平后的平台可能有成千上万个同高程格。这里**不按邻格编号随便选方向**，
也没有通过向高程叠加微小斜坡来掩盖问题：

1. 从所有“已确定出口的格”（有更低邻格，或本身在最外圈）出发做同高程
   反向 BFS，得到每个平台格到出口的跳数 `level`；
2. 每个平台格指向 `level - 1` 的同高程邻格，并列时取 `D8_ORDER` 中靠前者；
3. 由于 `level` 严格递减，平台路径必然走向真实出口，**不可能成环**。

### 10.4 编码

| 值 | 含义 | 说明 |
| --- | --- | --- |
| 0..7 | 图内八邻域方向 | 0=NW, 1=N, 2=NE, 3=E, 4=SE, 5=S, 6=SW, 7=W |
| 8 | OUTSIDE | 流出图像边界，仅最外圈有效格；**与 NoData 不同值** |
| 255 | NODATA | 无效格；栅格 NoData 也是 255；不是泄水口 |

`summary.json` 的 `direction_codes` 逐码写明 `row/col` 增量与方向名；
读者从任一有效格按编码逐格走，必然在有限步内到达 OUTSIDE。

### 10.5 上游贡献面积

```
contrib(i) = cell_area + Σ_{j 直接流入 i} contrib(j)
```

含像元自身面积；`cell_area = |dx| * |dy|`（投影米制）。沿拓扑序一次
累加完成，**不为每个测站重跑整图**。`contributing_area_m2.tif` 给出每个
有效格的值。

### 10.6 测站归属：两个口径必须分清

- **全上游贡献面积**：所有能沿流向图到达该测站的有效格面积之和（含测站
  格自身）。串联的上下游测站之间，上游站的面积真实流过下游站，因此
  **下游站的贡献面积包含上游站的全部贡献面积**。
- **独占分区**：每个有效格归给“它沿流向图**下游首先经过**的测站”（若
  该格本身是测站，则归它自己）。上游站的格子不会计入下游站的独占分区。
  这衡量的是“相对相邻站新增的汇水范围”，**不是贡献面积**。

两者对有效格互斥且完备：

```
Σ_测站 exclusive_area + unassigned_area = total_valid_area
```

未归属 = 一路流到图外且未经过任何测站。

传播一次完成：按拓扑序逆序计算
`first(i) = 测站自身 or first(直接下游) or 未归属`。

### 10.7 全局量

| 字段 | 定义 |
| --- | --- |
| `outside_area_m2` | 流出图总面积 = 以 OUTSIDE 为终点的格的上游面积之和 |
| `unassigned_area_m2` | 未归属面积（有效、但一路出图未经过测站） |
| `fill_volume_m3` | Σ(每格抬高量) × 像元面积 |
| `total_valid_area_m2` | 全部有效格面积 |

## 11. 输出

```
<output_dir>/
  filled_dem.tif              填洼高程 (m)，无效格 NoData
  pit_depth_m.tif             每格抬高量 (m)，只抬高不降低
  flow_direction.tif          D8 编码 (int16)，NoData=255
  contributing_area_m2.tif    全上游贡献面积 (m²)，含自身
  exclusive_partition.tif     独占分区：-1 无效, 0 未归属, k≥1 测站索引
  summary.json                输入身份/sha256/坐标/编码/固定规则/全局量/测站摘要
  stations.csv                同上摘要的 CSV 形式
```

`summary.json` 记录：DEM 的 sha256、CRS、仿射六参数、宽高、`dx`/`dy`、
NoData、dtype；测站 CSV 的 sha256 与个数；方向编码表；固定算法决策
（`algorithm_decisions`）；以及“本结果是地形推导的汇水边界，不代表洪水
水动力模拟”的免责声明。

## 12. 确定性与可复现

- 优先漫水堆元素为 `(高程, 索引)` 全序，结果与堆内部实现无关；
- D8 等坡度有固定顺序；
- 平台跳数由 BFS 唯一确定，`level - 1` 的选择有固定顺序；
- 测站索引按 `(row, col, outlet_id)` 排序分配，**CSV 行序翻转或打乱后
  方向、填洼、贡献面积、独占面积、摘要完全一致**；
- 面积累加只做加法，拓扑序由方向图唯一确定。

## 13. 演示与核对

```bash
.venv/bin/python -I demo/delineate_demo.py            # 六个手画矩阵 + 逐格核对
.venv/bin/python -I -m pytest tests/test_hydrology.py
```

演示覆盖：唯一缺口洼地（手算抬高量与体积）、需要走多格出水的平台、
长宽不同导致最陡方向改变、图内 NoData 岛、无外圈出口的孤立块（报错）、
上下游串联与分支测站。核对方式与主流程独立：

- 沿方向图逐格追踪，有效格都到 OUTSIDE 且不成环；
- 贡献面积 = 独立枚举的上游格面积之和；
- 独占分区不交叠，且与未归属部分恰好覆盖全部有效格；
- 翻转 CSV 行序后比较结果；
- 错误输入实际调用 CLI，确认退出码与原因。

# 雨量站累计翻斗读数整理：`rainfall`

纯本地、纯标准库的整理链（`flood_exposure/rain.py`），不接入网络，也不
import 或修改洪水栅格 / DEM 计算链。输入为读数 CSV
（`device_id,observed_at,cumulative_count`）与设备配置 JSON。

## 14. 核心口径：累计计数只确定区间雨量

翻斗计数器上报的是**累计读数**，本身不含雨的落点时刻。相邻两条有效读数
`c_i, c_{i+1}`（观测时刻 `t_i, t_{i+1}`）只能确定半开区间
`[t_i, t_{i+1})` 上的雨量：

```
rainfall([t_i, t_{i+1})) = (c_{i+1} − c_i) × tip_mm
```

输出逐段保留区间起止时刻，**不把雨量摊到任何更细的时刻，也不声称雨实际
落在区间内的哪一秒**；需要逐时刻雨强的下游使用方必须自行选择时间分配
假设，并对该假设负责。

### 14.1 时间归一化、去重与拒绝

* `observed_at` 必须带显式时区偏移，统一换算 UTC 后按
  `(device_id, 时刻)` 排序；缺时区直接拒绝，不猜测本地时区。
* 同设备同一 UTC 时刻的完全相同记录合并，合并掉的条数计入
  `merged_duplicate_records`，所有原始物理行号保留在
  `start_source_lines / end_source_lines`；同刻不同读数属于冲突，
  带行号报错并整体失败。
* 未知设备、负读数、非整数计数、缺列/多列表头分别明确拒绝；字段级坏行
  计入 `rejected_records`（附行号与原因），绝不静默忽略。

### 14.2 下降、回绕与重置

读数下降时只接受一种合法解释——配置了 `counter_modulus = M` **且**
前读数恰为高边界 `M−1`、后读数恰为低边界 `0`，此时按回绕补算
`delta = M − (c_i − c_{i+1})`（标记 `COUNTER_WRAP`，仍为有效段）。
其他任何下降（包括配了模数但没有严格跨过 `M−1 → 0` 的下降）一律视为
设备检修归零 / 复位：该段标记 `COUNTER_RESET`、无效、不写雨量，并以
后一条读数重新建立基准。未配置模数时不存在任何回绕解释。

### 14.3 禁止跨段相减的三类区间

下列区间写具体质量标记、`valid=false`、雨量留空，并从后一条有效读数
重新开始，事件在该位置强制截断：

| 标记 | 触发条件 |
| --- | --- |
| `GAP_TOO_LONG` | 区间时长严格大于 `max_interval_seconds`（相等仍有效） |
| `MAINTENANCE_WINDOW` | 半开区间与任一检修 `[start, end)` 相交；仅边界相碰不算 |
| `COUNTER_RESET` | 见 14.2 |

有效零雨段（读数不变）标记 `ZERO_RAIN`、`valid=true`、雨量精确为 0，
与无效段严格区分。

### 14.4 事件归并与截断

只把有效湿段（`OK` / `COUNTER_WRAP`）归入事件，零雨段不进事件、只累计
干旱时长：相邻湿段之间的干旱时长**严格大于** `dry_separation_seconds`
时拆成两场（相等仍同场）。无效段与超长空档必然截断事件，两侧的雨不会
拼成一场。事件列出起止时间、累计雨量、持续时间、最大单段雨量、湿段数，
以及 `truncated_by_data_boundary`：事件首/尾贴到该设备输入首/末读数
时刻时为 `true`，表示真实降雨过程可能延伸到观测覆盖之外。

### 14.5 输出、追溯与原子替换

* `rainfall_segments.csv`：逐段区间、起止计数与增量、每斗毫米、雨量、
  质量标记、有效性、两端的原始行号；
* `rainfall_events.csv`：事件汇总与数据边界截断标记、溯源行号；
* `rainfall_summary.json`：两份输入的 SHA256、归一化后的完整配置、
  读数/合并/拒绝/段/事件计数、逐标记与逐设备统计、被拒绝行明细。

雨量在输出层统一按 6 位小数呈现（`RAIN_MM_DECIMALS`），消除二进制浮点
尾差；所有有效性/回绕/事件判定都基于整斗增量与时长比较，不依赖该舍入。

三个文件都先写 `*.tmp`、`fsync` 后**回读比对**，再 `os.replace` 原子
替换；替换期间对已存在目标做 `.bak` 备份，任一步失败即回滚并清理临时
文件。配置错误或输入冲突在任何替换之前抛出，不会留下看似完整的新结果。
整理结果只依赖读数内容与归一化后的时刻，输入行序打乱后业务输出稳定
一致（溯源行号随物理行变化，但其引用的记录集合不变）。

# 应急撤离可达性：`evacuation-access`

纯本地、纯标准库的计算（`flood_exposure/evacuation.py`），不接入网络，也
不 import 或修改洪水栅格 / DEM / 雨量计算链。回答值班问题：**从某路口
出发，车能否赶在道路被淹以前到达仍开放的避险点？** 只看出发那一刻的
静态路况不够——车开到一半道路可能已经封闭；提前到达的路口也不一定允许
安全等待。因此搜索状态是**（路口, 分钟）**，而不是每个路口只记一次
最早到达。

## 16. 输入与时间模型

三份输入，全部使用相对同一参考时刻的**整数分钟**，不涉及地图匹配或
水动力预测：

* **路网 JSON**：`analysis_window`（`start_minute`/`end_minute`，声明的
  有限分析范围，时刻可落在端点上）、`intersections`（`node_id`、
  `can_wait`、`flooded_intervals` 受淹分钟区间）、`roads`（`road_id`、
  `from_node`/`to_node`、正整数 `travel_minutes`、可通行最大积水深度
  `max_depth_m`）、`shelters`（挂在路口上，若干 `open_windows`）。
* **积水 CSV**：固定四列 `road_id,begin,end,depth_m`，每条记录覆盖
  左闭右开区间 `[begin, end)`；`depth_m` 为非负有限数或空值（未知）。
* **查询 JSON**：`{"requests": [...]}`，每个请求给 `request_id`、
  `origin`、`depart_minute`、`deadline_minute`，时间都必须落在分析
  范围内。

整体拒绝（不出具任何看似可用的行程）的情形：路网重复编号、引用不存在
的路口、非正行驶分钟、非有限或负深度、越出分析范围的区间/片段、非法
结构（退出码 2）；积水片段越界、负深度/非有限深度、未知道路、**重叠
冲突**（已知与未知相撞，或已知深度不同）（退出码 3）；查询文件整体
结构非法（退出码 4）。重叠片段只有深度含义相同（都已知且相等，或都
未知）才可合并；相邻片段自然连用。

## 17. 路况与行程口径

* **未知不是干路**：没有记录的空档与空值深度一律视为未知；一段车程
  `[enter, exit)` 必须在**整个**区间上有已知且合格的路况——不只看
  端点，也不跨过中途的未知缺口。
* **压线可通过**：深度等于 `max_depth_m` 仍可通过，超过才不可通过。
  深度在内部以十进制 `Decimal` 比较，避免二进制浮点尾差影响“等于”
  判定。
* **半开区间**：车程恰在某封闭窗口开始的那一分钟结束时，道路检查不含
  抵达端点；但目的路口仍检查抵达当时是否受淹——抵达正在受淹的路口
  不合法。
* **等待**：在路口等待一分钟，要求该路口 `can_wait` 且这一整分钟安全
  （结束时刻同样不得受淹）；不能在道路中间停车。车辆只沿道路给定方向
  行驶，反向道路不可用。
* **避险点窗口左闭右开**：抵达关闭时刻不算赶上；提前到达时，若路口
  允许且能安全等待，可以等到窗口开放再计入抵达。
* **起点已受淹**：直接判 `invalid_request`，不把车辆凭空放到其他
  位置。

## 18. 搜索、优化顺序与终止性

状态 = (路口, 分钟)。所有道路耗时为正整数、状态分钟不超过截止分钟，
因此按分钟递增的单趟动态规划必然终止：处理到分钟 `m` 时，`(路口, m)`
的最优费用已经定型（所有入边都来自更早分钟）。每个状态只保留字典序
最小的 `(累计等待分钟, 道路编号序列)`——同一 `(路口, 分钟)` 下等待
相同的两条路径行驶分钟数必然相同，道路序列不可能互为前缀，所以该
支配规则是精确的；这也是“只记每路口最早到达”之所以不够的原因：
禁止等待的路口可能需要绕行后**更晚**抵达，才能接上后续开放的道路。

优化顺序（字典序）：

1. 最早抵达任一开放避险点（抵达分钟必须 `<=` 截止分钟）；
2. 累计等待分钟最少；
3. 道路编号序列的字典序最小。

若三者都相同（只可能等待位置不同），由时间递增的处理顺序确定，与
输入文件中道路/片段的排列次序无关；内部一律按编号排序后处理。

## 19. 输出、诊断与追溯

逐请求返回（单个请求无效不影响同批其他请求）：

* `reachable`：选中的避险点、抵达分钟、逐条道路的进入/离开分钟、
  在哪个路口等待了多久（连续等待合并为一段）、累计等待分钟；
* `unreachable`：搜索范围（出发/截止分钟、展开状态数、到达过的
  路口）与阻塞原因分类计数及示例——`depth_exceeded`（超深）、
  `unknown_conditions`（未知路况）、`waiting_not_allowed`（禁止
  等待）、`wait_blocked_by_flood`（等待被受淹阻断）、
  `arrival_node_flooded`（抵达时路口受淹）、`deadline_exceeded`
  （超过截止）、`shelter_not_open`（避险点未开放）。找不到路线
  既不是输入错误也不是成功撤离；
* `invalid_request`：具体原因（未知起点、出发晚于截止、时间越出
  分析范围、起点出发时已受淹、编号重复等）。

报告保留三份输入文件的 SHA256、分析范围参数与路网/路况规模摘要，
便于回头核对行程依据。`--output` 写出的报告先写临时文件、回读校验
再原子替换。

**适用边界**：结论只在已知路况与所给行驶时间假设下成立；未知路况
会阻断行程而不是被乐观忽略，积水上涨本身不是水动力预测出来的，而是
完全来自输入的积水片段。
